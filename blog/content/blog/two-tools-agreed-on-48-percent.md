We ran our mutation testing tool against mutmut's on the same fifteen Python projects and asked a blunt question: on the mutants you both tested, do you give the same verdict?

The answer, on 923 mutants both tools actually share: 444 agreements. 48.1 percent.

If you read that as "mutmut and moonbuggy disagree half the time, so somebody is wrong half the time," you would be reading it the way we did at first. That reading is wrong, and the reason it's wrong is the interesting part. Every one of the 573 disagreements has a written explanation in the repo, sorted into four categories, and only two of them are cases where mutmut recorded a kill that no test actually produces. We verified those by direct experiment. Both tools are mostly describing the same reality in different words, and the harness exists to make sure neither one can hide behind its own vocabulary.

## What the number measures, exactly

The comparison joins mutants on what the mutation *is*: the module, the original line, the mutated line, because the two tools share no identifiers. Both tools run against the same project, the same interpreter, the same dependencies. The subjects are fifteen projects: ten generated ones plus five pinned real libraries (more-itertools, boltons, humanize, sqlparse, tomli), each at a recorded tag, in its own virtualenv.

Not everything joins. Some mutations appear more than once in a file, so neither tool can prove which occurrence the other one tested. Those are excluded from the agreement number by construction, and listed as their own category rather than silently dropped. That is part of why the shared count is 923 and not the union of everything either tool generated.

The full table, per project, is generated by a script and checked for drift on every run. It lives at [the differential page](https://www.hamon.io/moonbuggy/differential.html) in the moonbuggy docs. Nobody edits it by hand.

## The four things a disagreement can be

Every disagreement in the table falls into one of four categories, and the harness exits with an error if anything lands outside them. Here is the whole of 573, by category:

| what the disagreement was | count |
|---|---:|
| both tools killed it; our verdict says *how* and theirs doesn't | 180 |
| no test covers the line, and the tools report that differently | 297 |
| the join was ambiguous; no pairing provable, so none asserted | 94 |
| mutmut recorded a kill, and direct experiment says otherwise | 2 |

Take them in order, because the order tells you what kind of disagreement dominates.

**Vocabulary difference: 180.** Both tools killed the mutant. moonbuggy additionally reports whether the kill came from a failed assertion or from the test erroring out; mutmut reads pytest's exit code, which is one bit, so it has one word for both. Nothing is wrong on either side. One tool reports more about the same event. (This is the same argument we made in the verdict-vocabulary post: KILLED is a fact, and *why* it was killed is the evidence. Half the disagreement total is this, and none of it is a correction of anyone.)

**Genuine semantic difference: 297.** The biggest bucket, and the most interesting to read, because both sides are defensible. The dominant case: a line with no test coverage — 267 of the 297. moonbuggy reports NO_COVERAGE, because an untested line is a finding: a different finding from "tested but not checked," but a finding. mutmut has no tests to run for that function, so it reports the run it could not make rather than the gap it found. Both are honest answers to different questions. The remaining 30: 27 are rows where a flaky covering test makes any confident verdict unsupportable (moonbuggy reports SUSPICIOUS where mutmut recorded a kill — every one of them is in one humanize function, the same one from the false-kill story below), and 3 come from mutmut deriving its own timeout budget, so the two tools time out different mutants. We are not claiming our answer is the right one; we are claiming both tools answer *a* question, and it is worth knowing the questions differ.

**Not actually the same mutant: 94.** The join is by mutation text, and some mutations repeat in a file. When a change appears twice (or six times, in one tomli parser loop), no pairing can be asserted, so none is. These carry no verdict information at all, which is why they are counted rather than guessed.

**Verified false kill: 2.** Two rows in the table, and behind them sits the part of the story we can prove. More on those below.

Add them up: 180 + 297 + 94 + 2 = 573. Zero unclassified. The harness refuses to write the table otherwise.

## The two false kills, and how "verified" was earned

In two cases, mutmut's table says KILLED and the evidence says no test fails under that mutation. The harness was built so that either tool's claim has to survive contact with the actual code, so each of those went to direct experiment.

The larger case: 123 mutants in one function of humanize's number formatting. mutmut records a kill for every one of them. We activated each of the 123 through mutmut's own machinery (the mutant tree first on the path, the environment variable set, exactly the way mutmut runs them), and the library's full 783-test suite stayed green for every single one. Then, because a green suite could theoretically just be a blind suite, we swept 22,210 inputs and found no output the mutation changes. The enclosing branch only runs where the mutation is arithmetically invisible. No test can kill it, and mutmut's recorded exit-1 came from a test-selection cache whose records outlived the collection they described. The smaller case is a decompression flag in boltons where the mutated value is arithmetically identical for every input the function can receive.

The mechanism names matter less than the discipline: for every claimed kill, we asked whether any test actually fails under the mutation, we ran the experiment, and we wrote down the answer. The ledger in `scripts/differential.py` pins the exact mutants and reasons, and a regression test checks that every ledger entry still classifies its own case, so the explanation cannot silently rot.

One more thing worth saying about this harness: it has caught bugs in our own tool, too. An earlier run surfaced a bug in moonbuggy's pytest session handling that made nearly every mutant on one library report a crash verdict where plain pytest kills them normally, and the fix shipped with its own regression test. The comparison is not a scoreboard; it is an instrument, and instruments get to point at their maker.

## What the 48.1% does and does not mean

What it does not mean: mutmut is 51.9% wrong, or that moonbuggy found 51.9% more. The dominant categories are two tools using different vocabularies and two tools answering different questions. The harness's own ground rules forbid treating either tool as the referee.

What it does mean: on every one of 923 mutants, we can tell you which of four things happened, and for the two categories where the tools genuinely contradict each other, we ran the experiment instead of trusting either side. The number that matters to us is not 48.1%. It is zero: zero unclassified, and zero verdicts in the ledger taken on faith.

For a developer choosing between these tools, the honest summary is narrower than either marketing page would give you: mutmut remains a solid, mature tool, and on the mutants where the tools' vocabularies overlap, they agree far more than the raw percentage suggests. Where they differ, the difference is usually about what gets reported, not what gets found. If reporting detail is what you need, read both tools' verdict vocabularies and decide which questions you want answered. That decision guide is the point of publishing this at all.

The full per-mutant table is in the docs, regenerated on every run, with every disagreement explained in place: [differential page](https://www.hamon.io/moonbuggy/differential.html).
